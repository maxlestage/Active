This page is for maintainers of the repository or of a fork. A release of the `active` crate takes one action: **change the version in `crates/active/Cargo.toml` and push it to `master`**, for example from `0.1.0` to `0.2.0`. Once CI passes, a GitHub Actions workflow tags the version, creates the GitHub release, tests the crate and publishes it on [crates.io](https://crates.io). Everything happens on the GitHub and crates.io websites, so a phone is enough.

## How the release workflow works

The workflow is `.github/workflows/release.yml`. It runs each time CI passes on a push to `master`, and:

1. **Reads the version** from `crates/active/Cargo.toml`. If its tag (`v0.2.0` for `0.2.0`) already exists, the version was released before and the workflow stops there.
2. **Tags and releases.** It creates the tag `v0.2.0` on the commit CI tested, and the GitHub release of the same name, with notes generated by GitHub from the commits since the previous release.
3. **Checks the token.** Without the `CARGO_REGISTRY_TOKEN` secret, the job ends with the warning "CARGO_REGISTRY_TOKEN secret missing — cargo publish skipped" and publishes nothing on crates.io.
4. **Runs the tests** with `cargo test -p active`. A failing test stops the publication.
5. **Publishes** with `cargo publish -p active --allow-dirty`, unless that version is already on crates.io.

A GitHub release published by hand (step 4 below) runs the same publication: the version is then read from the release's tag, `v0.2.0` giving `0.2.0`, and written into `crates/active/Cargo.toml` before publishing. A tag that does not look like `v1.2.3` (optionally with a pre-release suffix such as `-beta.1`) stops the workflow with an error.

## 1. Create a crates.io token

1. Open [crates.io](https://crates.io) and tap **Log in with GitHub**.
2. Open your avatar menu, then **Account Settings**. Add and **verify your email address**: crates.io refuses to publish without one.
3. Open **API Tokens** and tap **New Token**.
4. Name it, for example `github-release`, and choose an expiration date.
5. Select the scopes **publish-new** (needed for the very first release, which creates the crate) and **publish-update** (for later versions).
6. Tap **Generate Token** and copy it right away: crates.io shows it only once.

## 2. Add the secret to GitHub

The GitHub mobile app does not show repository settings, so use the website in your phone's browser.

1. Open the repository on github.com, then **Settings**.
2. Open **Secrets and variables**, then **Actions**.
3. Tap **New repository secret**. Name: `CARGO_REGISTRY_TOKEN`. Secret: paste the token. Tap **Add secret**.

The name must match exactly. Nobody can read a secret back once saved; to replace it, update it with a new value.

## 3. Bump the version

1. In the repository, open `crates/active/Cargo.toml` and tap the pencil icon (**Edit**).
2. Change the `version = "…"` line in the `[package]` section, for example from `0.1.0` to `0.2.0`.
3. Tap **Commit changes** and commit to `master` (or to a branch: the auto-merge brings it into `master` once CI is green, and starts the release itself).

That commit is the release: once CI passes on it, the workflow tags `v0.2.0`, creates the GitHub release and publishes the crate. There is no form to fill in.

Follow [semantic versioning](https://semver.org): before `1.0.0`, bump the minor number (`0.1.x` to `0.2.0`) for breaking changes or new features, and the patch number (`0.2.0` to `0.2.1`) for fixes only. Cargo treats `0.1.x` and `0.2.x` as incompatible.

## 4. Publish a release by hand (optional)

Not needed after step 3. A release published by hand still publishes the crate, for example for a version whose tag you want to create yourself:

1. Open `https://github.com/<owner>/Active/releases/new` (or **Releases**, then **Draft a new release**).
2. Tap **Choose a tag**, type `v0.2.0` (the version from step 3 with a `v` in front) and select **Create new tag on publish**.
3. Keep `master` as the target.
4. Set the title, for example `v0.2.0`. **Generate release notes** lists the merged changes for you.
5. Tap **Publish release**.

## 5. Check the result

Open the **Actions** tab: a **Release** run appears once the **CI** run of the push has passed. A green check means the crate is published (or that the token was missing: open the run to see the warning). Then:

- **Releases** shows the new tag `v0.2.0` and its notes;
- [crates.io/crates/active](https://crates.io/crates/active) shows the new version;
- [docs.rs/active](https://docs.rs/active) builds the API documentation a few minutes later, with the `client` feature enabled.

### If something fails

- **CI fails:** nothing is tagged or published. Fix the code and push again: the version is released as soon as CI passes.
- **Tests fail in the Release run:** the tag and the GitHub release exist, but nothing is on crates.io. Fix the code, then bump to the next patch version and push.
- **The version already exists:** crates.io never accepts the same version twice, even after a yank. Release the next version.
- **401 or 403:** the token is missing, expired or lacks the right scope. Create a new one and update the secret.
- **The name belongs to someone else** (first release only): another account owns `active` on crates.io. Rename the package in `crates/active/Cargo.toml` (for example `active-web`) and update the docs.

## Publishing from a computer

The same release without GitHub Actions:

```sh
cargo login                         # paste the crates.io token once
cargo test -p active
cargo publish -p active --dry-run   # builds the package exactly as it will be uploaded
cargo publish -p active
```

Only the files listed in the crate's `include` (`src`, `README.md`, `LICENSE`) are uploaded. `cargo package -p active --list` shows them. Push the version bump to `master` afterwards: the workflow creates the tag and the GitHub release, and skips crates.io since that version is already there.

## Continuous integration

`.github/workflows/ci.yml` runs on every push and pull request:

| Step | Command |
| --- | --- |
| Format | `cargo fmt --all --check` |
| Lint, server | `cargo clippy --workspace --all-targets -- -D warnings` |
| Lint, browser | `cargo clippy -p active --features client --target wasm32-unknown-unknown -- -D warnings`, then the same for the site and the examples (`--lib`) |
| Test | `cargo test --workspace` |
| Build the site | the same commands as [Heroku](../deploy-heroku/) (`RustConfig` and `heroku-build.sh`) and the `Dockerfile` |
| Package | `cargo package -p active --allow-dirty` |

The last step catches packaging problems (a missing file, invalid metadata) before a release does.

The workflow also has a `merge` job: when a branch is pushed and every check above passes, it merges that branch into `master` and pushes the result. Branches whose name starts with `wip/` and pull requests are only checked, never merged automatically. After the merge, with Heroku's automatic deploys enabled, the change goes online on Heroku, which serves the website.
