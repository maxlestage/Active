---
title: Benchmarks
description: Active measured against Leptos, Dioxus, Yew, Sycamore, maud and hand-written HTML: server rendering, WebAssembly size and time to interactive.
---

`active` was compared with the main Rust web frameworks on three questions: how fast does the server render a complete page, how much WebAssembly does the browser download for a small interactive component, and how soon is that component usable. Everything is Rust: the pages, the servers, and the harness that drives Chromium. The whole suite is in `bench/`.

## Summary

| | Active | Best of the others |
| --- | ---: | ---: |
| Server render of a product page | 5.58 µs | 5.19 µs (Leptos, hand-written `<head>`), 13.44 µs with leptos_meta |
| WebAssembly + glue for a counter (gzip) | **36.8 kB** | 45.8 kB (Sycamore) |
| Interactive, 100 ms network latency | **224.2 ms** | 226.7 ms (Sycamore) |

- **Smallest bundle.** The counter island ships 36.8 kB gzip in total, 20% less than Sycamore, 40% less than Leptos and 4.6 times less than Dioxus.
- **Fast server rendering with real SEO.** Among the frameworks that merge SEO tags from components into the `<head>` (`active`'s `Document`, Leptos with leptos_meta), `active` is 2.4 times faster. Only Leptos writing the whole `<head>` by hand in one template is slightly faster (7%).
- **Interactive as soon as the bundle runs.** The four hydrating frameworks are within a few milliseconds of each other; the download dominates, so the smaller bundle helps on slow networks.

> **Note:** these numbers come from one machine (Intel Xeon 2.8 GHz, 4 cores, Rust 1.97, Chromium 141). Compare the frameworks with each other, not with your own hardware.

## Server rendering

Every implementation renders the same complete document for product page `i`, with `i` changing on every iteration: `<html lang="en">`, a `<head>` with 11 SEO tags (title with a template, description, canonical, Open Graph, Twitter) and one JSON-LD script, and a `<body>` with an `<h1>` and a list of 30 items. Each output is checked tag by tag before timing. Each implementation runs in its own process, warms up for 1 s, then renders for 3 s in batches of about 10 ms; the table shows the median of three runs.

| Implementation | µs / page | Pages / s | vs hand-written |
| --- | ---: | ---: | ---: |
| maud 0.27 | 1.37 | 729 288 | ×0.68 |
| Hand-written (`push_str`/`write!`) | 2.01 | 497 191 | ×1.00 |
| Leptos 0.8, `<head>` written by hand | 5.19 | 192 686 | ×2.58 |
| **active** | **5.58** | **179 083** | **×2.78** |
| Leptos 0.8 + leptos_meta | 13.44 | 74 406 | ×6.68 |
| Yew 0.23 | 17.17 | 58 257 | ×8.53 |
| Dioxus 0.7 | 24.22 | 41 281 | ×12.04 |
| Sycamore 0.9 | 33.01 | 30 298 | ×16.41 |

maud and the hand-written page are templates: they only write strings. `active` builds a component tree, collects the `Seo` of every component and merges them into the head, which is the work a real site needs. It writes straight into one `String`, without a virtual DOM, and most elements need no allocation beyond their text.

## WebAssembly size

The same counter in every framework: a button that increments the number next to it, rendered by the server and taken over by the browser. Built for `wasm32-unknown-unknown` with the size-optimized profile (`opt-level = "s"`, `lto`, `panic = "abort"`), then `wasm-bindgen --target web --no-typescript`, without `wasm-opt`. The total includes the JavaScript glue generated by wasm-bindgen.

| Framework | Browser mode | .wasm | .wasm gzip | Glue gzip | Total gzip |
| --- | --- | ---: | ---: | ---: | ---: |
| **active** | island hydration | 81.6 kB | 32.4 kB | 4.3 kB | **36.8 kB** |
| Sycamore | hydration | 105.8 kB | 41.1 kB | 4.7 kB | 45.8 kB |
| Leptos | hydration | 144.9 kB | 54.8 kB | 6.2 kB | 60.9 kB |
| Yew | hydration | 241.8 kB | 90.0 kB | 6.3 kB | 96.3 kB |
| Dioxus | client-side render | 426.9 kB | 155.4 kB | 15.0 kB | 170.4 kB |

> **Tip:** the benchmark counter records timings with a floating-point number, which pulls Rust's float formatting into every bundle. Without it, the `hello` example is about 22 kB gzip. See [performance](../performance/) for the size of each kind of app and how to shrink a bundle further.

## Time to interactive

Headless Chromium loads each counter page 21 times per network profile, with the HTTP cache disabled, alternating between frameworks. Each app writes `performance.now()` into the page when its WebAssembly starts and when the button is interactive; the harness reads these marks through the DevTools protocol and finally clicks the button for real (the number must go from 3 to 4).

| Framework | Localhost: median (min–max) | 100 ms latency: median (min–max) | Start → interactive |
| --- | ---: | ---: | ---: |
| Yew | 25.3 ms (21–38) | 227.8 ms (225–239) | 0.8 ms |
| **active** | 25.5 ms (21–42) | **224.2 ms (221–232)** | 0.6 ms |
| Leptos | 25.5 ms (22–38) | 227.2 ms (222–239) | 0.5 ms |
| Sycamore | 25.7 ms (21–33) | 226.7 ms (222–392) | 0.5 ms |
| Dioxus | 41.3 ms (32–58) | 339.3 ms (332–351) | 1.0 ms |

The hydrating frameworks overlap within their ranges: treat them as tied. Dioxus renders on the client (its hydration needs its own full-stack server) and its glue imports extra files, which costs one more network round trip.

## Run it yourself

```sh
rustup target add wasm32-unknown-unknown
cargo install wasm-bindgen-cli --version 0.2.129
cd bench
cargo run --release -p runner                    # everything, about 3 minutes after the first build
cargo run --release -p runner -- ssr             # one part: ssr, wasm, browser or report
BENCH_PRINT=1 cargo run --release -p ssr-active  # print the page an implementation renders
```

The runner finds Chromium on the `PATH` (or set `CHROME=/path/to/chrome`). It writes `bench/RESULTS.md` and the raw data in `bench/results/`. The method, the version of every framework and the choices made for each one are described in `bench/README.md`.
