# Benchmark results

Generated by `cargo run --release -p runner` (method, caveats and how to run it: [README.md](README.md); raw data: [`results/`](results/)). The numbers come from one machine: compare the frameworks with each other, not with other machines.

## Summary for `active`

- **Server rendering**: 5.58 µs per page, ×2.78 the hand-written baseline (rank 4 of 8).
- **Bundle**: 36.8 kB gzip in total for the counter (rank 1 of 5).
- **Browser**: interactive after 25.5 ms (localhost; rank 2 of 5; loads from 21 to 42 ms) and 224.2 ms (100 ms RTT; rank 1 of 5; loads from 221 to 232 ms).

## 1. Server-side rendering

Every implementation renders the same complete document for product page `i` (`i` changes on every iteration): `<html lang="en">`, a `<head>` with the 11 SEO tags (`<title>` with the template `Produit {i} · Acme`, description, canonical, `og:title`, `og:description`, `og:type`, `og:url`, `og:image`, `og:site_name`, `twitter:card`, `twitter:site`) and one JSON-LD script, and a `<body>` with an `<h1>` and a `<ul>` of 30 `<li>Option {k} — {i·k} €</li>`.

Each implementation runs in its own process. Before timing, its output is checked tag by tag (each SEO tag exactly once, in `<head>`, with the expected value; the JSON-LD; the `<h1>`; the 30 items). Then it renders for 1.0 s to warm up and for 3.0 s in batches of about 10 ms; a run's result is its median batch (µs per page). The table shows the median of 3 run(s), started in turn so that a noisy moment does not hit a single implementation. p10–p90 is the spread of the batches in the median run.

| --- | --- | ---: | ---: | ---: | ---: | ---: |

How each page is produced:

- **Hand-written**: `push_str`/`write!` into one `String`, values escaped.
- **maud**: `html!` compile-time template.
- **active**: components + `Seo` merged into `<head>` by `Document`.
- **Leptos + leptos_meta**: `<Title>`/`<Meta>`/`<Link>`/`<Script>` injected at `<MetaTags/>` (as leptos_axum does).
- **Leptos (plain `<head>`)**: whole document in one `view!`, `to_html()`.
- **Dioxus**: `rsx!` `head`+`body`, `VirtualDom` + reused `dioxus_ssr::Renderer`.
- **Yew**: `html!` document, `LocalServerRenderer` on a current-thread Tokio runtime.
- **Sycamore**: `view!` document, `render_to_string`.

Page bytes differ slightly: void elements written `<meta>` or `<meta/>`, hydration markers (Leptos `<!>`, Yew `<!--<[]>-->`, Sycamore `data-hk` attributes and `<!--/-->`), leptos_meta's `<!--HEAD-->` and `active`'s `<style>active-island{display:contents}</style>`.

## 2. WebAssembly bundle size

Built for `wasm32-unknown-unknown` with the `wasm-release` profile, then `wasm-bindgen --target web`; no `wasm-opt`. "JS glue" is every JavaScript file wasm-bindgen generated (the module and its snippets), each compressed on its own. gzip is level 9. kB = 1000 bytes.

## 3. Browser: time to interactive

Headless Chrome/141.0.7390.37, driven from Rust with chromiumoxide (no JavaScript evaluated). Each counter page (server HTML + bundle, served by a small Rust server on 127.0.0.1) is loaded 21 times per network profile after one warm-up round, in turn with the other apps (one load of each, then again), with the HTTP cache disabled; the table shows medians. The app writes `performance.now()` (milliseconds since navigation start) into `<body data-start>` when its wasm starts and `<body data-ready>` when the button is interactive; the runner reads them with DOM queries. "100 ms RTT" adds 100 ms of latency to every request (`Network.emulateNetworkConditions`, bandwidth not limited). Every page then gets one real click: the number must go from 3 to 4.

| Framework | Browser mode | Interactive, localhost: median (min–max) | Interactive, 100 ms RTT: median (min–max) | wasm starts | wasm start → interactive | Click 3 → 4 |
| --- | --- | ---: | ---: | ---: | ---: | :---: |
| Yew | hydration (`Renderer::hydrate`) | 25.3 ms (21–38) | 227.8 ms (225–239) | 24.5 ms | 0.80 ms | ✅ |
| **active** | island hydration (`active::hydrate`) | 25.5 ms (21–42) | 224.2 ms (221–232) | 24.8 ms | 0.60 ms | ✅ |
| Leptos | hydration (`hydrate_body`) | 25.5 ms (22–38) | 227.2 ms (222–239) | 25.1 ms | 0.50 ms | ✅ |
| Sycamore | hydration (`sycamore::hydrate`) | 25.7 ms (21–33) | 226.7 ms (222–392) | 25.1 ms | 0.50 ms | ✅ |
| Dioxus | client-side render (`dioxus::launch`) | 41.3 ms (32–58) | 339.3 ms (332–351) | 40.4 ms | 1.00 ms | ✅ |

"wasm starts" (when the module's start function runs: HTML, JavaScript and WebAssembly fetched and compiled) and "wasm start → interactive" (the framework's own work: hydration, or the first render for client-side rendering) are measured on localhost. `performance.now()` has a 0.1 ms resolution in Chromium (pages are not cross-origin isolated). When `data-ready` is recorded:

- **active**: after `active::hydrate` returns (synchronous).
- **Leptos**: after `leptos::mount::hydrate_body` returns (synchronous).
- **Dioxus**: first `use_effect` (after the first render is applied to the DOM).
- **Yew**: first `use_effect_with` (after the hydrated render is committed).
- **Sycamore**: after `sycamore::hydrate` returns (synchronous).
